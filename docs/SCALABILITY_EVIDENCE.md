# Scalability evidence — 2026-08-24 (audit gap 6)

First quantitative scalability pass: a production-shaped **1.1M-row** `CampaignMetric` volume (25 workspaces, deliberately skewed so the three largest hold ~79k rows each — approximating the heaviest pilot agency at ~160k rows/year pace) exercised through the **real hot-path query shapes** extracted from `warehouse-query.ts`, `dashboard-overview.ts`, and `metrics/query/route.ts`.

## Methodology

- Ephemeral PostgreSQL 16 container (same major version as production/CI), migrations applied via `prisma migrate deploy`.
- Data generated by `scripts/bench/scalability.ts` (committed — rerunnable): 25 workspaces × 4 connections × 180 days × ad-grain entities, with skew.
- Each query run with `EXPLAIN ANALYZE` using realistic parameters (largest workspace for worst case, mid workspace for typical). Full plans preserved in [evidence/scalability-bench-plans-20260824.txt](./evidence/scalability-bench-plans-20260824.txt).
- Write path benchmarked as 200 deterministic upserts against a hot conflict row.

> **Caveat:** absolute milliseconds are from a local container, not Neon compute. The durable signals are **plan shapes** (zero sequential scans — every query is index-backed) and relative scaling behavior, both of which transfer.

## Results

| Query | Shape | Execution |
|---|---|---|
| Q1 | Warehouse page: newest-first page of 1001, largest workspace | **23–27 ms** |
| Q1b | Same + 30-day range + platform filter | **3–5 ms** |
| Q2 | Filtered count | **8–10 ms** |
| Q3 | Freshness aggregate (`MAX(pulledAt)`) | **22–25 ms** |
| Q4 | Dashboard 7-day currency rollup | **~1 ms** |
| Q5 | Explorer campaign groupBy, ordered, LIMIT 1000 | **25 ms** |
| Q6 | Deterministic upsert (hot conflict row), avg of 200 | **0.09 ms** |
| Q7 | Cross-workspace isolation probe (nonexistent tenant) | **0.09 ms** |

All queries return inside interactive budgets (<50 ms) at 1.1M rows with zero sequential scans. The composite indexes shipped by migrations (`workspaceId_accountId_date`, `workspaceId_platform_date`, `connectionId_date`) carry every read shape; Q1's top-N sort stays in memory at 389 kB.

## Findings & recommendations

1. **No index work required at pilot scale.** Headroom is large: extrapolating linearly, the current shapes should hold interactive budgets to roughly **5–10M total rows / ~500k per heavy workspace**, i.e., well beyond the 20-agency pilot ceiling.
2. **Q1/Q5 are the first to age** (sort-heavy on the biggest workspace). If they ever exceed budget, the fix is a `(workspaceId, date DESC, id DESC)` covering index — pre-validated by the plan showing a top-N heapsort over an index scan today.
3. **Retention proposal (data-driven):** archive/delete `CampaignMetric` rows older than **24 months** per workspace once any workspace crosses ~400k rows, keeping the working set under the proven envelope. Implement as part of `health-tick` when the trigger first fires; not needed now.
4. **Write path is not a bottleneck**: 0.09 ms average upsert latency means sync throughput is bounded by provider APIs, not the database.
